## 1.0 Overview & Purpose

This document provides a technical overview of the "A's Server Bot" service. It serves as a companion to the bot's System Requirements Specification, detailing the architectural decisions, logical flow, and core concepts of the implementation.

The primary purpose of the bot is to act as a secure, interactive, and maintainable management layer for the "AO" home server. It provides tools for monitoring and managing containerised services via a Discord interface.

## 2.0 System Architecture & Best Practices

The bot is designed to run as a fully containerised service within the existing Docker environment. The architecture prioritises security, maintainability, and alignment with the server's "single source of truth" philosophy.

### 2.1 Containerisation

- **Orchestration:** The service is managed via a `docker-compose.yml` file located at `C:\server\config\aserver-bot\`. This file defines the bot's runtime environment, including network access and volume mounts.
    
- **Image:** The bot runs on a custom Docker image built from a `Dockerfile`. This image uses a standard Python base and installs all necessary libraries from a `requirements.txt` file, ensuring a reproducible and isolated environment.
    
- **Security Context:** The bot container is granted secure, **read-only** access to the host's Docker socket (`//var/run/docker.sock`). This allows the bot to query the Docker daemon for live container information. **Best Practice:** Limiting this to read-only access by default reduces the attack surface. Write-actions (like `!restart`) are handled via authenticated API calls, with permissions managed internally by the bot's code, not by the container's base permissions.
    

### 2.2 Configuration & Secrets Management

All configuration, especially sensitive credentials, is externalised from the codebase.

- **Environment File:** All secrets (Discord Token, API keys) and configuration variables (Admin Role Name, service URLs) are stored in a `.env` file. This file is explicitly loaded by the bot at startup and is the single source of truth for configuration. **Best Practice:** This is a critical security measure. The `.env` file should be included in server backups but must never be committed to version control.
    

### 2.3 Code Architecture: Modularity via Cogs

To ensure long-term maintainability, the bot's codebase is not monolithic. It uses the `discord.py` "Cogs" framework to break down functionality into logical, self-contained modules. This is a deliberate choice to prevent a single, unmanageable `bot.py` file.

- **`bot.py` (Core Engine):** This script is the central loader. Its sole responsibilities are loading secrets, establishing connections (to Discord and Docker), and discovering and loading all available Cogs. It also manages the global `on_message` event handler that implements the ephemeral response model.
    
- **`cogs/` Directory (Functional Modules):** This directory contains a separate Python file for each major feature set. This structure makes the codebase easier to navigate, debug, and extend. For example, all Docker-related commands reside in `services.py`, while all media-related commands are in `media.py`.
    

## 3.0 Core Logic & Data Flow


### 3.2 Service Discovery: The Docker Labelling Standard

The bot discovers which services to manage by reading metadata directly from Docker container labels. This avoids hard-coding and makes the system self-configuring. Any container with the label `homelab.bot.managed="true"` is recognised.

### 3.3 Interactive Workflow: The `discord.ui.View` Model

The media search workflow is a stateful, interactive session managed by a `discord.ui.View` object.

1. **Initiation:** A user's command creates an instance of a `View` class in memory.
    
2. **State & Components:** This class is initialised with the data from the API call (e.g., search results) and defines the UI components (buttons, menus) and their associated callback functions.
    
3. **Event Listening:** The `View` is attached to a message and listens for interaction events from Discord. When a user clicks a button, the `View` executes the correct callback.
    
4. **Stateful Actions:** The callback can modify the original message (e.g., disable buttons after a request is sent), send new messages, or perform external API calls. The `View` automatically times out to prevent orphaned listeners.
    

## 4.0 Developer Guidance & Areas to Watch For

This section details key learnings from the development and debugging process. Any future developer working on this bot should pay close attention to these points to avoid common pitfalls.


### 4.2 **Critical Area: Docker Label Application**

The bot's service discovery is entirely dependent on Docker labels. A common point of failure is when labels are added or changed, but the bot does not reflect the updates.

- **The Redeployment Imperative:** Docker only reads `labels` from a `docker-compose.yml` file when a container is **created**. Simply restarting a container is not sufficient. After editing labels for a service, you **must** force Docker to recreate it by running `docker-compose up -d --force-recreate` in that service's config directory.
    

### 4.3 **Best Practice: Defensive API Handling**

During the development of the Jellyseerr integration, we discovered its API can return inconsistent data types (e.g., a status can be a string or an integer) and may omit fields entirely for certain results.

- **Never Trust API Payloads:** All code that interacts with an external API must be "defensive". Never directly access a nested key like `result['mediaInfo']['status']`.
    
- **Use Safe Accessors:** Always use methods like `.get('key', default_value)` to safely access dictionary keys, which prevents crashes if a key is missing.
    
- **Handle Data Types:** Before performing operations, check the type of the data received. If expecting a string, explicitly cast it with `str()` to handle cases where an integer might be returned. This prevents `AttributeError` exceptions and makes the bot far more resilient.
