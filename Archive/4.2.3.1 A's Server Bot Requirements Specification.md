This document outlines the complete functional and non-functional requirements for "A's Server Bot", a bespoke Discord bot designed to provide an interactive management and access layer for the home server "AO".

#### **1.0 Core Principles**

The bot shall be engineered to reflect the core management philosophy of the homelab system.

- **1.1. Single Source of Truth:** The bot must derive all its information directly from the live services it interacts with (e.g., the Docker socket, Jellyseerr API). It shall not rely on manually maintained static files for its core functions, ensuring data is always accurate and up-to-date.
    
- **1.2. User-Centric & Interactive:** The user experience is paramount. Commands must be intuitive, and responses should guide the user through a logical workflow using interactive components like buttons and select menus where appropriate.
    
- **1.4. Seamless Integration:** The bot shall act as a native interface to the server ecosystem, leveraging the APIs of existing services (Jellyseerr) as the engine for its actions rather than duplicating functionality.
    
- **1.5. Maintainability & Self-Documentation:** The bot should be designed for long-term maintainability. Features like the help system must be self-updating to prevent documentation drift.
    

---

#### **2.0 Interaction and Privacy Model**

The bot's interaction model is designed to maintain clean public channels while providing users with private, powerful workspaces.

- **2.1. Ephemeral Responses:** All commands that return user-specific or administrative data (e.g., `!search`, `!status`) must, when invoked in a public server channel, respond with an **ephemeral message** visible only to the command author.
    
- **2.2. Command Deletion:** Upon receiving a valid command in a public channel, the bot must immediately delete the user's triggering message to prevent channel clutter.
    
- **2.3. Full DM Functionality:** All bot commands must be fully functional when sent to the bot via Direct Messages (DMs). This provides a persistent, private command history for each user.
    
- **2.4. Interaction Persistence:** Ephemeral responses for commands that produce valuable output (e.g., `!search`) must include a `[Save to DMs]` button, which sends a persistent copy of the message to the user's DMs.
    
    

---

#### **3.0 Help & Command Discovery**

The bot must provide a user-friendly way for users to discover its capabilities.

- **3.1. General Help (`!help`):**
    
    - **3.1.1. Trigger:** `!help`
        
    - **3.1.2. Functionality:** Responds with a categorized list of all commands
        
    - **3.1.3. Output:** A Discord embed, categorised by function (e.g., "Media Services", "Administrator Tools").
        
- **3.2. Specific Help (`!help <command>`):**
    
    - **3.2.1. Trigger:** `!help search`
        
    - **3.2.2. Functionality:** Responds with detailed information for a single command.
        
    - **3.2.3. Output:** A Discord embed containing the command's purpose, usage syntax, and practical examples.

#### **4.0 Features

These commands are designed for convenience and general access.

- **4.1. Command: `!links` (or `!services`)**
    
    - **4.1.1. Purpose:** To provide a simple, clean "menu" of all services.
        
    - **4.1.2. Data Source:** Filters Docker containers for the label `homelab.bot.managed="true"`.
        
    - **4.1.3. Output:** A simple embed containing a list of hyperlinks formatted with each service's friendly name (e.g., • `[Jellyfin](<URL>)`).
        
  **4.2. Command: `!search`**
	    
	 **4.2.1. Purpose:** To initiate the interactive media search and request workflow.
	        
     **4.2.2. Syntax:** Must parse both general (`!search Title`) and specific (`!search Title, YYYY`) queries.
	        
	 **4.2.3. Initial Response:** The bot will present the single most relevant search result in a rich embed containing:
	        
	    - Media Poster (thumbnail)
	            
	    - Title and Year
	            
        - Availability Status (✅ Available / ❌ Not on Server)
	            
        - Streaming Information (if not available on server)
	            
	       - Brief Synopsis
	            
	 **4.2.4. Interactive Workflow:**
	        
	    If available, the bot presents a `[Watch on Jellyfin]` button. Clicking this provides the user with a direct link to the media on the Jellyfin server.
	            
	    If unavailable, the bot presents a `[Request This Movie]` button. Clicking this sends a request to the Jellyseerr API and confirms the action to the user.
	            
	    All initial responses will include a `[That's Not It]` button. Clicking this presents a dropdown select menu with the next 3-4 search results, allowing the user to refine their choice and trigger a new rich embed for the selected item.
            
- **4.3. Command: `!status`**
    
    - **4.3.1. Purpose:** To provide a real-time health check of all managed services.
        
    - **4.3.2. Syntax:** `!status` (for all services) or `!status <service_name>` (for one).
        
    - **4.3.3. Output:** A detailed embed report containing each service's name, live status (Running, Stopped), role, public URL, and private URL.
        
- **4.4. Command: `!logs`**
    
    - **4.4.1. Purpose:** For quick, remote diagnostics of a container.
        
    - **4.4.2. Syntax:** `!logs <service_name> [lines]` (defaults to 20 lines).
        
    - **4.4.3. Output:** The requested log lines formatted in a Discord code block.
        
- **4.5. Command: `!restart`**
    
    - **4.5.1. Purpose:** To restart a specific service container.
        
    - **4.5.2. Syntax:** `!restart <service_name>`
        
    - **4.5.3. Security (CRITICAL):** The bot _must_ verify the user has the Administrator role on the Discord server before executing this action.

#### **6.0 Non-Functional & Technical Requirements**

- **6.1. Security:** All API keys, tokens, and service URLs must be loaded at runtime from the `.env` file located at `C:\server\config\aserver-bot\.env`. They must not be hard-coded.
    
- **6.2. Docker Labelling Standard:** The bot will identify and configure services based on a standard set of Docker labels applied in their respective `docker-compose.yml` files:
    
    - `homelab.bot.managed="true"` (Required to be seen by the bot)
        
    - `homelab.bot.name="Friendly Name"` (Required)
        
    - `homelab.bot.description="Service role..."` (Required)
        
    - `homelab.bot.url="https://public.url"` (Required for user-facing links)
        
    - `homelab.bot.localurl="http://local.url"` (Required for status checks)
        
        
- **6.3. Performance & Reliability:** All external API calls must implement a reasonable timeout (10-15 seconds). The bot must indicate it is processing a request by displaying Discord's "typing..." status.
    
- **6.4. Error Handling & Debugging:** The bot must handle common errors gracefully (e.g., API offline, invalid query, missing API key) and provide clear, user-friendly error messages. It must be resilient to unexpected or malformed data from APIs and must not crash.
